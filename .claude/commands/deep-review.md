Deep code review of a single project in the forge-of-games solution.

Review ONLY the target project. Treat every other project as read-only context — you may look up their public symbols with Serena to understand a call, but do not review or report on their internals.

Step 0 — tracker & target:
- Ensure `${REVIEW_DIR}/README.md` exists; if it doesn't, create it from the .sln (a project table with ⬜ pending statuses + an empty "Cross-project patterns to check" section).
- Resolve ${PROJECT}: if an argument was passed, ${PROJECT} = that argument; otherwise read the tracker and take the FIRST project still marked ⬜ pending — the next one in the order the setup step established. If no argument was passed and nothing is pending, stop and tell me the review is complete. State which project you're reviewing and why (explicit argument vs. next pending) before doing anything else.
- Read the tracker's "Cross-project patterns to check" list; while reviewing ${PROJECT}, explicitly verify whether each of those patterns occurs here and report any hits under the appropriate severity.
- Enumerate every hand-authored source and config file in ${PROJECT}, whatever the extension — not just `.cs`/`.razor` but also code-behind (`.razor.cs`), `.cshtml`, `.proto`, `.csproj`, `appsettings*.json`, scoped CSS/JS interop, and anything else present. Mark which files fall under the exclusions below. This list is your coverage checklist; you're accountable for every non-excluded file appearing in the report's coverage manifest.

How to work:
- COVERAGE IS MANDATORY. Review every non-excluded file and every symbol in ${PROJECT}. Do not skip a file because it looks trivial — interfaces, abstract/partial classes, models, DTOs, records, enums, extension methods, constants, and .razor markup all get reviewed. If you catch yourself deciding a file isn't worth reading, that is the signal to read it.
- EXCLUSIONS (the only files you may skip):
  · Auto-generated code. Detect it, in order, by: a `// <auto-generated>` header at the top of the file; a generated-marker filename (`*.g.cs`, `*.g.i.cs`, `*.razor.g.cs`, `*.Designer.cs`, `*.AssemblyInfo.cs`, `*.GlobalUsings.g.cs`); living under `obj/` or `bin/`; or protobuf-net output generated from the .proto files. This means the `.g.cs`-style marker segment — NOT merely containing the letter "g": `Manager.cs`, `Configuration.cs`, `LoggingBehavior.cs` are ordinary source and MUST be reviewed. For EF Core migrations, the migration `.cs` (Up/Down) is reviewed; only its `.Designer.cs` and the ModelSnapshot are generated and skipped.
  · `.resx` resource files. These are translation/string data — large and not worth reviewing. Don't open them; just list them as skipped resources in the manifest.
- Read the code, not just the shape. Use get_symbols_overview to ENUMERATE all files/symbols — but that map is an index, not a review; then read the body of every symbol (find_symbol with the body, or the whole file for small ones). Never judge a method from its signature alone. Read wiring/config in full: Program.cs, DI registration, .csproj, appsettings, migrations.
- Use Serena where it earns its keep: find_referencing_symbols before flagging any public type/member, to gauge real blast radius; read any Serena memory for this project/solution first for context.

Review for (apply the stack-specific items only where this project actually uses that tech):

Correctness & safety
- Logic bugs, boundary/off-by-one, wrong LINQ, culture-sensitive string/number handling, equality/GetHashCode mistakes.
- Nullability (Nullable is on everywhere): unsafe `!`, missing null checks on external input, suppressed warnings.
- Async: sync-over-async (.Result/.Wait/GetAwaiter().GetResult()), async void, unobserved/fire-and-forget tasks, missing CancellationToken threading, ConfigureAwait in library code.
- Exceptions & FluentResults: is Result<T> used consistently vs exceptions-as-control-flow? Empty catches, catch(Exception) too broad, swallowed or wrongly-rethrown errors.
- Resource & lifetime: undisposed IDisposable/IAsyncDisposable, `new HttpClient` (should be IHttpClientFactory), DbContext lifetime/threading, static mutable state, DI captive dependencies (e.g. a singleton capturing a scoped DbContext).
- Security: untrusted input into FromSqlRaw/interpolated SQL, deserializing untrusted protobuf/LZString, missing authorization on endpoints, secrets in source/appsettings, over-broad CORS, PII in logs.

Performance
- EF Core: N+1, missing AsNoTracking on reads, client-side evaluation, loading full entities where a projection/ProjectTo would do, tracking inside loops, chatty round-trips.
- Allocations / hot paths, needless materialization, sync IO on hot paths.

Design & maintainability
- Layering violations, domain entities leaking through the API surface, DTO/mapping smells.
- Duplication, dead or commented-out code, over-long methods, magic values, naming, inconsistency with the rest of the codebase's conventions.

Stack-specific
- Blazor WASM (MudBlazor/Syncfusion): OnInitialized vs OnInitializedAsync misuse, components subscribing to events/timers without IDisposable (leaks), gratuitous StateHasChanged, heavy render loops, large per-component state, JS interop disposal, EditForm/validation gaps.
- MediatR: handlers doing too much, pipeline behavior ordering, missing validation behavior.
- AutoMapper: unmapped members, mappings that trigger DB/lazy loads, Map vs ProjectTo against EF.
- Durable Functions: orchestrator determinism — no DateTime.Now/Guid.NewGuid/Random/direct IO/non-durable async inside orchestrators (must use context APIs); correct activity boundaries, idempotency, retry/poison-message handling, fan-out/fan-in.
- Azure Functions (isolated): trigger/binding correctness, expensive static init hurting cold start, blocking calls.
- protobuf-net wire DTOs: tag stability/back-compat, surrogate correctness, nullable/required handling.
- EF Core (FogDbContext): mapping correctness, migration parity, cascade deletes, concurrency tokens.
- TFM constraint: if ${PROJECT} is Shared, Models.Hoh, Inn, or InnModels.Hoh (net8.0; Shared is C#12), flag any net9-only API or C#13 syntax.

Output — write to `${OUTPUT}`:
- Findings grouped by severity: Critical (bugs, security, data loss, concurrency) / High (correctness risk, resource & lifetime, perf hotspots) / Medium (design, maintainability) / Low (nits).
- Each finding: short title · location (`Path/File.cs` + symbol, line if easy) · what's wrong and the concrete impact · suggested fix (small code sketch if it helps) · for public symbols, the blast radius from find_referencing_symbols.
- "Test coverage gaps": the solution has no tests — list the highest-value units/paths in THIS project to test first, and why.
- "Cross-project concerns": anything that looks solution-wide; also append it to the "Cross-project patterns to check" section in `${REVIEW_DIR}/README.md` so later projects get checked against it.
- "Coverage manifest": list every source/config file in ${PROJECT} with its disposition — ✅ reviewed, ⛔ generated (name the marker that identified it), or ⏭️ resource (`.resx`, skipped). Every file that isn't generated or a resource must be ✅. This is the proof that nothing was silently skipped.

Rules:
- Review only — don't modify source. Propose changes, don't apply them, unless I ask.
- Be specific and evidence-based; cite the symbol. If you're unsure something's a real problem, say so and give the tradeoff — don't assert.
- Signal over volume: a few real Critical/High findings beat fifty nits. Don't pad.
- Judge against the codebase's own conventions, not personal taste.
- When finished, flip ${PROJECT} to ✅ in `${REVIEW_DIR}/README.md` with a one-line summary (counts by severity).
